## 2. 현재 탄소중립플랫폼 현황 분석

### 2.1 시스템 및 화면 구조 (FO/BO)
- **사용자 사이트 (Front-Office)**: 일반 기업 고객 및 사용자가 탄소 배출량을 입력하고 리포트를 확인하는 서비스 플랫폼.
  - 별도의 챗봇 화면이나 대화형 인터페이스 미존재.
  - 정적인 화면 구조로 구성되어 사용자 동선 내 맥락에 맞는 즉각적인 도움말 제공의 한계가 있음.
- **관리자 사이트 (Back-Office)**: 운영자가 배출량 산정 로직, 사용자, 공지사항, 매뉴얼 등을 관리하는 백오피스.
  - 메뉴 단위 관리 및 조회/수정 기능 제공.
  - AI 기반의 자동화된 문서 처리나 자연어 기반의 지식 관리 기능 미비.

### 2.2 인증 및 권한 구조
- **SSO 연동**: Google OAuth2 기반의 SSO 로그인 지원 중.
- **권한 체계**: 플랫폼 전체를 관리하는 '관리자(Admin)'와 기본 조회를 담당하는 '직원(Employee)'의 단일 프로젝트 기반 이분화된 구조 적용 중.
- **한계점**: 타 프로젝트(DPPA, 비즈나루 등) 확장을 위한 멀티 테넌시(Multi-Tenancy, Workspace 격리) 및 그에 따른 권한 위임(프로젝트 관리자 등) 체계가 부재함.

### 2.3 문서 / FAQ / 매뉴얼 관리 방식
- **현재 관리 방식**: 관리자 사이트 게시판 형태의 FAQ 및 매뉴얼 파일 업로드(PDF, HWP 등) 기능 제공. 사용자는 게시판에서 키워드로 단순 검색하거나 파일을 직접 다운로드하여 열람.
- **한계점**:
  - 문서 내 구체적인 정보를 찾는 시맨틱(의미) 검색 불가.
  - 도메인 특화 지식(탄소 배출권, 산정 방식 등)에 대한 복합적 질의(관계형 질의) 대응 불가.

## 3. 사내 멀티 프로젝트 챗봇 도입 시나리오

단일 탄소중립 챗봇이 아닌 **사내 공통 프로젝트 지식 챗봇 플랫폼**을 도입할 경우의 아키텍처 및 업무 변화.

### 3.1 챗봇 적용 시 영향 영역
1. **Front-End (사용자/관리자)**
   - 각 사내 프로젝트(탄소중립, DPPA, K-Ads 등) FO 사이트에 공통 챗봇 위젯(스크립트 또는 웹 컴포넌트) 삽입 필요.
   - BO 사이트에 단일 플랫폼 관리가 아닌 'Workspace(프로젝트) 단위' 관리 및 전환(Switching) UI 추가 필요.
2. **Back-End (API & DB)**
   - 모든 API 요청 시 어느 프로젝트(Workspace)의 지식을 검색해야 하는지 식별자 전달 체계 도입.
   - DB 테이블 최상단에 `workspace_id` 컬럼 추가 및 권한 격리 로직 필수화.
3. **Data Pipeline (인덱싱)**
   - 프로젝트 도메인마다 문서의 종류와 양식이 다르므로(예: DPPA 정산 매뉴얼 vs 탄소중립 배출권 법령), 도메인별 최적화된 청킹 및 엔티티(Entity) 추출 지침 분리 필요.

## 4. 기존 분석/설계 산출물의 누락(개선) 필요 항목 식별

초기 탄소중립 챗봇 전용으로 설계된 기존 산출물 대비, 멀티 플랫폼 전환 시 보완해야 할 항목들입니다.

| 기존 산출물 영역 | 보완/개선 필요 사항 |
|---|---|
| **도메인 정의** | 탄소중립 외 DPPA 등 타 도메인 확장을 위한 'Workspace' 개념 신설 |
| **권한 구조** | System Admin(전체)과 Workspace Admin(프로젝트 개별) 분리 등 5단계 Role 정의 |
| **데이터 모델** | `graphrag_sources`, `chat_sessions` 등 모든 지식 및 로그 테이블에 `workspace_id` FK 추가 |
| **API 명세** | 각 조회 및 관리 API Endpoint에 Workspace 컨텍스트를 주입하는 헤더 또는 Path Variable 설계 |
| **관리자 UI** | 전체 플랫폼의 현황 대시보드 추가, 특정 Workspace 설정 화면 진입 플로우 재설계 |

---

## 5. 요약 및 시사점
현재 탄소중립플랫폼은 정적인 지식 관리와 단일 프로젝트 구조로 되어 있습니다. 이를 사내 지식 챗봇 플랫폼으로 확장하기 위해서는 **Workspace 기반의 다중 테넌트(Multi-Tenant) 아키텍처 도입**이 가장 시급한 과제이며, 이에 따른 **데이터 격리(Data Isolation) 및 권한 통제 체계 재설계**가 프로젝트의 성공적 확장의 핵심입니다.
