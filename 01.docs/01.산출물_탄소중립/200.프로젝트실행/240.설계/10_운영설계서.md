## 2. 인덱싱(지식 갱신) 운영 정책
- **백그라운드 처리**: 대용량 PDF 파싱 및 LLM 그래프 추출(인덱싱)은 메인 API 서버와 분리된 Celery 워커(또는 백그라운드 태스크)에서 비동기로 실행되어 챗봇 응답 성능을 저하시키지 않습니다.
- **실패 시 재처리 (Retry)**: 인덱싱 중 일시적인 네트워크 장애나 LLM Rate Limit 초과 시, 자동 3회 재시도(Exponential Backoff)를 수행하며, 최종 실패 시 상태를 `FAILED`로 기록하고 알림을 발송합니다.
- **재인덱싱 정책**: 원본 문서의 내용이 개정될 경우 기존 버전의 청크/엔티티 데이터를 우선 논리 삭제(또는 백업) 후 새 문서로 재인덱싱합니다.

## 3. 품질 개선 (오답/미응답) 프로세스
AI 환각(Hallucination) 방지 및 품질 고도화를 위한 루프.
1. **모니터링**: 운영자(Operator)가 BO 사이트의 [미응답 질문 관리] 및 [피드백 관리(싫어요)] 메뉴를 주기적(일 1회 등)으로 검토.
2. **원인 분석**: 근거(Source)가 부족한 것인지, 프롬프트의 문제인지 식별.
3. **지식 보강**: 누락된 지식이면 관리자가 단답형 FAQ를 등록하거나 관련 문서를 스크랩하여 추가 업로드(인덱싱).
4. **검증**: BO의 [챗봇 테스트 (Sandbox)] 화면에서 동일 질문을 입력하여 답변 품질이 개선되었는지 확인.

## 4. 백업 및 복구 (Backup & Recovery)
- **Database**: PostgreSQL (vectordb)는 매일 새벽 3시(KST) 전체 논리 백업(pg_dump) 수행 및 일주일 치 보관.
- **Storage**: 업로드된 원본 문서(PDF 등)는 S3 호환 Object Storage에 저장되며, 버전 관리(Versioning)를 활성화하여 실수로 인한 삭제 방지.
- **복구 테스트**: 분기별 1회, 백업본을 Staging 환경에 복원(Restore)하는 모의 훈련 수행.

## 5. 배포 환경 (Dev / Stg / Prod)
- **Dev (개발)**: 신규 기능(멀티 테넌트 추가 등) 및 로컬 디버깅용.
- **Staging (검증)**: 배포 전 실 서비스와 동일한 DB 스키마 복제본에서 QA 테스트 진행.
- **Production (운영)**: Nginx 로드밸런싱 및 Multi-Worker(Gunicorn) 환경 기반 안정적 서비스.
- **CICD 파이프라인**: GitLab CI 또는 GitHub Actions를 통한 자동 빌드(Docker Image) 및 무중단 배포(Rolling Update).

## 6. 모니터링 및 알림 (Monitoring & Alerts)
- **시스템 메트릭**: CPU, Memory, DB 커넥션 뷰어 (Grafana/Prometheus 활용 권장).
- **비즈니스 메트릭**: 전체 토큰 사용량 일일 집계(API 비용 산정용), 질의 실패율, 평균 응답 시간(Latency).
- **알림 (Alert)**: 장애 발생(HTTP 500 연속 발생), 인덱싱 작업 실패, 토큰 일일 한도 초과 위험 시 사내 메신저(Teams/Slack) 및 이메일 즉시 발송.
